# 设计说明

README 只保留入口级信息，这里是实现层面的取舍。

## 依赖方向

```
入口层（cli / api / scripts）
        ↓
agent/loop  ──►  llm/client  ──►  外部模型 API
        ↓
tools/      ──►  storage/    ──►  文件 / SQLite
        ↓
agent/context（纯函数，不依赖任何一层）
```

- `loop` 不知道数据存在哪，只调用 `execute_tool`
- `tools` 不知道用哪个模型，只接收名字与参数
- `llm` 不知道对话历史从哪来，只接收 `messages` 列表

## 存储抽象

待办有两个后端（`storage_json` / `storage_sqlite`），实现同一套 `load_todos` / `save_todos`，
由 `STORAGE_BACKEND` 决定，入口层零改动即可切换。

异常按父子类分层：`TodoStorageCorruptError` 是父类，JSON 与 SQLite 各有子类。
入口层只捕获父类，因此后端之间的错误处理保持一致。

会话数据（`storage_session`）单独一个库 `data/agent.db`，不纳入这个工厂，也不受
`STORAGE_BACKEND` 影响——待办是业务数据，会话是运行时状态，两者生命周期不同。

## 工具层约定

- 永远返回字符串。`role=tool` 的 `content` 必须是字符串，失败时也返回
  `{"ok": false, "error": "..."}`
- 失败不抛异常。错误信息回传给模型，让模型自行决定重试、换工具还是直接回答
- 注册表与分发集中在 `tools/__init__.py`，新增工具只改 `TOOL_SCHEMA` 和 `_HANDLERS`
  两处；分发用 `handler(**args)`，顺带把参数校验也做了

计算器不使用 `eval`：模型生成的表达式是不可信输入，改用 `ast` 白名单，只放行数字、
四则运算与括号。

## 上下文管理

- token 数取自 API 返回的 `usage`，不自行估算
- 单次请求的 `prompt_tokens` 超过预算 75% 时触发裁剪
- **裁剪单位是「对话轮」而不是消息条**：`assistant(tool_calls)` 与 `tool` 必须同进同出，
  拆开会导致下一次请求 400
- 保留 `system` 与最近 N 轮：丢的是中段历史细节，保的是 system 规则、最近上下文连续性、
  工具调用配对完整

已知取舍：纯滑动窗口会失忆，被丢弃的旧信息模型确实想不起来。摘要压缩与关键信息保留
留给后续的上下文工程。

另一个观察：工具定义（`tools` 字段）随每次请求重发，是固定开销。工具越多，这部分越贵，
需要在工具描述精细度与提示词成本之间权衡。

## 会话持久化

- 消息整条序列化存进 `payload` 列，不拆字段。原因是 `tool_calls` 与 `tool_call_id`
  是一对，拆列再拼回去最容易在这里还原出错
- 落库是**全量覆盖**而不是增量追加：裁剪会删消息，增量表达不了删除
- 恢复会话依赖三件事配合：`messages` 本身就是纯 dict 列表 → 存取无损 →
  `run(task, messages=...)` 接受外部历史并在尾部追加新问题

## 异常与失败策略

只有「工具自身失败」会被转成消息交给模型；网络、密钥、存储层面的失败直接向上抛，
由调用方熔断。这是当前的刻意取舍：只有工具失败时，模型才有机会换策略。

重试、超时、降级、死信队列属于后续的可靠性专题，不在当前实现范围内。

## 测试策略

- 存储与接口层：临时目录隔离，不污染 `data/`
- 上下文层：纯函数，直接断言分组与裁剪结果
- 工具层：用内存版 storage 替身，不落盘
- 循环层：把 `app.agent.loop.chat` 换成按脚本返回的假函数，只验证控制流

这样测试不依赖网络与密钥，跑一次不到一秒。
